# 多协议调试工具规格

Status: ready-for-agent

更新日期：2026-10-22。本文汇总 Q1–Q36 已确认结论，以及本轮确认的测试入口和 VS Code 开发环境，作为当前产品规格发布到本地 issue tracker。实施顺序为 **Modbus RTU → UPP/CAN → Modbus TCP**；各阶段的资料依赖仍须满足。

2026-10-23 增量变更：[多窗口、参数表与插件界面规格](../multi-protocol-workbench-ui/spec.md) 已发布。调试窗口、参数展示、插件编辑页面、保存／应用分离及基础曲线的要求以该变更规格为准；本文未涉及变更的通信、数据一致性和阶段约束继续有效。

## Problem Statement

操作人员需要类似 Modbus Poll / Slave 的桌面工具，既能作为 Modbus 主站读写和轮询真实设备，也能作为从站模拟数据与应答，并接入既定的自定义协议 UPP。多个调试会话需要同时运行，每个会话访问或模拟同一协议下的多个设备。

如果连接、组包、请求管理和界面相互耦合，新增协议或传输就需要修改主体。仅将字节转换为字段的编解码接口也无法承载轮询、超时、重试和从站应答。操作人员需要简洁的日常界面，同时能够回溯原始证据，定位解析失败、断线或写入结果不确定等问题。

从站模拟数据需要由外部 JSON 管理，支持导入、即时修改和显式保存。工具必须明确区分运行数据、磁盘文件和真实设备写入，让操作人员控制通信与数据变更。

## Solution

提供基于 Windows x64、Qt 6 和 Qt Widgets 的桌面工作台，围绕调试会话组织报文列表、发送/读写面板、Modbus 数据视图和回溯入口。开发使用 VS Code；根据本机安装固定 Qt 6.12.0、LLVM-MinGW Clang 22.1.7、CMake 3.30.5、Ninja 1.12.1 和 C++17。

主体管理插件、会话生命周期、传输通道和记录；协议插件管理协议交互、数据模型、配置、操作与可选专用视图。新协议和传输通过配套编译的插件接入，重启后加载，在既有 SDK 能力范围内保持主体代码稳定。协议与传输必须是明确支持的组合。

| 交付阶段 | 支持组合 | 可见能力与验收结果 |
| --- | --- | --- |
| 第一阶段 | Modbus RTU / 串口 | 主站读写和轮询；从站多设备模拟与应答；公共插件、记录、工作区和 Widgets 界面 |
| 第二阶段 | UPP / CAN | 按真实 UPP 规范完成一组消息的发送、接收和解析，验证自定义协议扩展 |
| 第三阶段 | Modbus TCP | 主站读写和轮询；从站多客户端、多 Unit ID 模拟与应答；整体扩展和交付验证 |

第一阶段提供 RTU 可用闭环，三个阶段共同构成本规格范围。UPP 文档稍后提供，RTU 可以先推进；UPP 产品实现仍遵循第二阶段顺序。

## User Stories

1. 作为操作人员，我希望在 Windows x64 上使用 Qt 桌面工具，以便完成设备通信调试。
2. 作为操作人员，我希望先获得 Modbus RTU 主站和从站的可用版本，以便优先调试串口设备。
3. 作为操作人员，我希望创建多个独立调试会话并同时运行，以便并行观察不同端点。
4. 作为操作人员，我希望分别运行主站和从站会话，以便在合法端口拓扑下联调。
5. 作为操作人员，我希望每个会话绑定一个端点、一种协议和多个设备，以便管理同一链路上的设备集合。
6. 作为操作人员，我希望端点占用冲突有明确提示，以便修正端口配置。
7. 作为操作人员，我希望只使用已声明支持的协议与传输组合，以便避免无法工作的搭配。
8. 作为操作人员，我希望一个 RTU 主站会话访问同一串口总线上的多个地址，以便集中调试多台从站。
9. 作为操作人员，我希望主站统一安排总线请求，以便多个设备的操作不会互相打断。
10. 作为操作人员，我希望读取线圈、离散输入、保持寄存器和输入寄存器，以便检查设备状态与数据。
11. 作为操作人员，我希望通过支持的单个或多个写入功能修改线圈和保持寄存器，以便执行设备操作。
12. 作为操作人员，我希望配置轮询及周期，以便持续更新主站观测值。
13. 作为操作人员，我希望地址明确采用从 0 开始的 PDU 地址，以便避免地址偏移错误。
14. 作为操作人员，我希望区分正常应答、协议异常、超时和传输错误，以便判断下一步操作。
15. 作为操作人员，我希望在会话级配置读取重试次数、应答超时和重试间隔，以便适应当前链路。
16. 作为操作人员，我希望额外读取重试次数可设为 0，以便只进行一次尝试。
17. 作为操作人员，我希望轮询周期与重试间隔分别配置，以便控制正常采样和失败重试。
18. 作为操作人员，我希望设备写入和参数设置不自动重试，以便避免设备重复执行。
19. 作为操作人员，我希望未确认写入保留结果不确定的提示和记录，以便自行决定是否再次执行。
20. 作为操作人员，我希望断线时结束未完成操作，并可选择重连后恢复轮询，以便继续调试。
21. 作为操作人员，我希望重连后不自动补发未确认写入，以便由我控制设备操作。
22. 作为操作人员，我希望看到简明的连接状态、结果和错误提示，以便承担主要恢复操作。
23. 作为操作人员，我希望一个 RTU 从站会话模拟多个设备地址，以便测试主站访问多设备的行为。
24. 作为操作人员，我希望每个模拟设备拥有独立的四类数据区，以便分别配置地址范围和数值。
25. 作为操作人员，我希望主站观测值与从站模拟数据分开管理，以便理解数据来源。
26. 作为操作人员，我希望每个模拟从站绑定一份外部 JSON，以便独立管理其数据。
27. 作为操作人员，我希望从站启动时读取并校验全部必需文件，以便确认启动数据有效。
28. 作为操作人员，我希望文件缺失、不可读或无效时阻止对应会话启动并显示设备、路径和原因，以便修复问题。
29. 作为操作人员，我希望文件错误不影响界面及其他会话，以便继续其他调试工作。
30. 作为操作人员，我希望导入 JSON 完整校验后整体替换目标数据，以便应用明确的数据配置。
31. 作为操作人员，我希望导入失败保留原有数据，以便保护当前模拟环境。
32. 作为操作人员，我希望导入后继续手动编辑，以便快速调整数值。
33. 作为操作人员，我希望有效的改值、整份导入和地址范围调整立即影响后续请求，以便无需停止会话。
34. 作为操作人员，我希望每条请求使用一致的数据视图，以便应答不会混合替换前后的数据。
35. 作为操作人员，我希望通过保存按钮写回当前文件并可另存为，以便保留可复用配置。
36. 作为操作人员，我希望文件保存与真实设备写入独立操作，以便明确控制各自效果。
37. 作为操作人员，我希望替换或重新加载前遇到未保存修改时可以保存、放弃或取消，以便保护修改。
38. 作为操作人员，我希望运行中的外部文件变化不自动改变已加载数据，以便保持模拟行为稳定。
39. 作为操作人员，我希望下次启动重新读取 JSON，以便使用明确保存的启动数据。

## Implementation Decisions

1. **平台与工具链。** Windows x64、Qt 6.12.0 的 LLVM-MinGW 构建、Qt Widgets、Clang 22.1.7、C++17、CMake 3.30.5 和 Ninja 1.12.1，开发使用 VS Code。按用户实际安装选择配套组合，已通过独立验证程序的 Debug/Release 编译与运行。构建与测试通过命令行复现，产品宿主与插件采用同套工具链和 Qt 构建。
2. **宿主模块。** 工作台提供会话列表、概要、记录和视图容器；插件宿主管理发现、兼容性、能力声明和工厂；会话宿主管理启停、端点占用、运行代次和事件分发。主体依能力声明调用插件，不按协议名称增加特殊分支。
3. **协议模块。** 协议会话承接组帧/拆帧、解析、校验、角色行为、操作验证、轮询、应答关联、超时、读取重试和从站数据。输入为用户操作、接收数据、连接变化、发送结果及计时事件；输出为发送意图、消息、操作结果和诊断。纯 feed/encode 不能替代协议会话。
4. **通道模块。** 通道服务管理端点、连接身份、异步收发和有限发送队列，传输插件执行实际 I/O。协议不能绕过公共入口自行打开串口或网络连接。通道保留流块、帧、数据报的边界及实际元数据，不解释协议。
5. **视图扩展。** 协议插件提供配置/操作声明与可选 QWidget 视图，Modbus 寄存器视图归 Modbus 插件。后续绘图允许通过 QQuickWidget 嵌入 QML，协议核心保持独立 C++ 模块；当前不实现绘图。
6. **插件交付。** 协议和传输插件在启动时发现、校验和加载，更新后重启。按配套应用、SDK、Qt 与工具链构建组合交付；工具链版本已按本机安装固定，项目 SDK 版本和 ABI 仍须通过最小插件验证。对象存活期间对应插件代码保持加载。
7. **加载失败处理。** 缺失、不兼容或加载失败只禁用依赖功能和会话，保留插件身份及原始配置并提示原因。保存工作区不能删除暂时无法解释的配置；修复并重启后可恢复。这不构成进程内插件崩溃隔离保证。
8. **支持组合。** 校验声明的协议、角色、传输与必要能力。UPP 规范不可修改，CAN ID、路由、帧格式、分片、应答规则等待真实资料，不能靠忽略必要元数据迁移承载。超出已发布 SDK 表达能力的新需求应显式演进接口版本。
9. **实现组件。** Qt Serial Port、QCanBus、Qt Network 分别作为串口、CAN、网络的候选基础。Modbus 选择自有实现或可注入外部 I/O 的组件；自行管理连接的 QModbus 完整栈不能直接作为纯编解码器。COMMS Library 仍为 UPP 候选，待真实规范和验证决定。
10. **会话与设备。** 一个会话拥有一个配置端点、一种协议实例和设备集合；冲突端点明确拒绝。RTU 一个串口管理多个地址，同一总线由一个主站统一调度在途请求。多个会话可同时运行，但不能重复占用冲突的物理通道。
11. **TCP 映射。** 主站一个远端 IP:端口一个会话，可有多个 Unit ID，不同远端分别建会话。从站一个监听端点接受多客户端并提供多个 Unit ID。逐连接隔离解析和事务关联，同一 Unit ID 的模拟数据共享并串行更新。
12. **Modbus 范围。** 四类数据区为线圈、离散输入、保持寄存器和输入寄存器；支持十六进制功能码 01、02、03、04、05、06、0F、10 及对应异常响应。基础值为布尔和 16 位寄存器，PDU 地址从 0 开始。主站观测值与从站模拟数据分离。
13. **读取重试。** 会话级配置默认额外重试 2 次、单次应答超时 1000 ms、重试间隔 100 ms；2 次额外重试表示最多 3 次尝试，0 次禁用。轮询周期独立。可重试失败由协议明确规定，协议异常不一律重试，未知 UPP 指令不猜测读写属性。
14. **写入与恢复。** 设备写入和参数设置不自动重试，手动再次执行形成新操作。断线结束未完成操作，可选重连恢复轮询，不补发未确认写入。后端接受或本地发送完成不等于设备确认，超时不能证明设备没有执行。
15. **记录模型。** TraceRecord 表达原始数据及发送/状态/诊断事件，Message 表达识别出的协议消息，Operation 表达用户操作及尝试、进展和结果。消息与记录通过稳定引用及字节区间多对多关联，被动消息不必归属操作。概念类型尚未冻结为可编译 SDK。
16. **原始证据。** 输入经统一记录入口再解析，解析失败和未识别数据仍可记录。CAN 专属字段留在传输元数据和原始记录中，Message 通过来源引用展示。区分主机观测时间、单调时钟和可选硬件时间戳，不虚构后端精度。
17. **容量与过载。** 采用进程内有界缓存、后台批量记录、GUI 批量刷新；近期缓存、写入队列与磁盘留存均有限。通信不等待磁盘或逐条绘制；过载允许记录丢失，显示数量及时间范围，与正常过期分别表达。丢失提示不能仅靠向已满队列追加记录。
18. **回溯与导出。** 按消息、操作、时间查询，手动导出 CSV 概要或 JSONL 详细记录。JSONL 包含所选范围内实际可用的原始字节、元数据和关联，并标记缺失来源；导出期间轮换或淘汰也不能静默遗漏。用户主动开启磁盘记录用于长期或跨重启回溯。
19. **存储扩展。** 回溯模块内部区分写入与存储实现，首版使用本地存储。Redis 仅为实测后可选的异步后端，不是首版依赖，不发布存储插件 SDK，也不预设 Redis 能解决界面或持续慢消费问题。
20. **从站 JSON。** 一份外部 JSON 对应一个模拟设备，表达四类数据区、地址范围和数值；多设备、连接和轮询归工作区。字段可按设计需要扩展，版本、未知字段和往返规则由实施明确，不提前冻结全部字段。
21. **启动依赖。** 从站会话通信前读取并校验所有必需 JSON，任一缺失、不可读或无效则整个对应会话不启动，提示设备、路径和原因；界面和其他会话继续可用。不得以内嵌快照或默认零值替代缺失文件。
22. **运行数据与保存。** 编辑、整体导入和地址范围调整校验后立即影响目标设备的后续请求，每条请求使用一致视图；失败保留原数据。保存将当前数据写回文件，支持首次选择路径和另存为；保存不触发真实设备写入，也不是运行数据生效条件。
23. **替换与重载。** 未保存修改在覆盖或重新加载前提示保存、放弃、取消。仅启动会话或主动导入时读取文件；运行中外部修改/删除不热加载，下次启动重新校验。一次运行中的自动重连不等于重新启动会话。
24. **工作区。** 保存会话、设备、轮询、通信/重试参数、布局和外部文件引用，打开后先恢复配置，由操作人员启动通信。路径解析、导入后绑定及保存一致性等技术规则由接口实现任务验证，满足上述行为。
25. **执行与生命周期。** GUI 对象在 GUI 线程管理，协议和通道状态在所属上下文串行处理；文件等待及界面刷新不阻塞通信。停止时拒绝新操作、取消轮询/计时、结束未完成操作并释放端点；运行和连接代次防止旧回调影响新会话。线程数、队列和刷新周期通过测量确定。
26. **实施顺序。** 按 RTU → UPP/CAN → Modbus TCP 推进软件实现与验证。2026-10-24 用户明确将硬件条件和实际物理验收后置，不再用物理验收阻塞下一阶段软件开发；仍须具备阶段所需的协议规范和预期结果。软件使用可控传输、协议样例及适用的软件对端验证，真实串口/CAN 的互通、时序和负载验收保留为独立待办，不能用软件结果代替；分别记录环境、证据和限制。
27. **CAN 首个软件切片。** 用户于2026-10-24确认Q1–Q3：先做原始经典CAN帧观察，支持标准/扩展格式，每帧数据最多8字节，远程/错误帧按后端实际提供的信息保留和标识；CAN FD后置。沿用已确认的窗口、左侧操作栏、主数据区及随窗记录，展示时间、方向、CAN ID、格式/类型、长度及原始字节，支持筛选和CSV/JSONL导出。CAN ID暂不解释为设备地址，首片不做UPP重组、CRC判断、参数值解析或产品发送功能。
28. **无硬件验收入口。** 采用独立虚拟CAN样例源，经正式Qt SerialBus接收后端进入会话界面；提供可启动样例源及操作说明，明确标注软件测试来源。首片不增加抓包文件导入或定时回放。虚拟后端不能产生的特殊帧用可控输入补测并区分证据；实际硬件互通继续后置。
29. **分阶段解除依赖。** 旧14的14A为上述原始帧观察，14B为UPP接收重组与解析。14A不依赖UPP歧义解决；14B仍依赖CAN路由/重组、CRC、长度和相关交互格式确认。只有14B软件通过并具备发送规则后才进入旧15；14A通过不冒充完整UPP接入。必要的通用帧能力匹配与空帧记录扩展在14A实施，不在主体加入按协议名称判断的业务逻辑；发送元数据契约留待旧15按实际需求演进。

## Testing Decisions

用户已于 2026-10-22 确认：**以调试会话的公开接口作为主要测试入口**，从启动、停止、读写、导入和编辑观察结果、发送数据、模拟数据和回溯记录。底层注入可控传输与时钟，真实串口/CAN 另做互通验证。

- 好的测试验证外部行为：发出的数据、操作结果、数据生效、端点释放和回溯证据。避免断言私有缓冲区、内部类拆分、锁、队列容器或辅助函数调用顺序。
- 主要入口覆盖会话宿主、协议会话、通道协作、Modbus 数据和记录关联；可控时间验证超时/重试，文件使用隔离的临时数据。
- 插件发现、兼容与销毁补充少量插件宿主边界测试；Widgets 配置、未保存提示和视图挂载补充少量界面流程验证。主要入口不能表达契约时才增加测试边界。
- 当前尚无产品代码或产品测试框架；已新增独立工具链验证程序，用 CTest 验证 Debug/Release 构建和基础 Qt 模块运行。它不替代后续会话与协议行为测试，也不构成硬件互通证据。

| 验证范围 | 必须观察的行为 |
| --- | --- |
| 会话与占用 | 多会话并行、冲突端点失败、停止释放资源、旧运行回调不改变新会话 |
| RTU 协议 | 八个功能码、异常、CRC、拆分输入、错误帧、静默时间与统一总线调度；规范向量和独立参考对端交叉验证 |
| 读取重试 | 默认最多三次尝试、额外次数 0 时一次、超时/间隔/轮询独立、按会话生效 |
| 写入与恢复 | 超时/断线/重连不自动重复写入；本地发送不冒充设备确认；手动再次执行为新操作 |
| 数据与 JSON | 四类区和多设备隔离、有效导入整体替换、无效保留旧数据、请求视图一致、编辑即时生效与保存独立 |
| 启动与工作区 | 所有必需文件有效才启动对应会话；文件变化不热加载；再次启动重新读取；恢复配置不自动通信 |
| 保存 | 保存/另存为与提示有效；失败不丢修改；写文件期间的新修改不误标为已保存；路径和格式往返一致 |
| 记录与导出 | 解析失败仍有原始证据；跨块/一块多消息关联正确；发送和应答区分；过期/丢失进入查询和导出 |
| 过载 | 注入慢记录后端和界面负载，验证资源有界、通信继续、丢失统计可见，测量持续负载及延迟 |
| 插件 | 缺失/不兼容只禁用依赖、未知配置不丢、最小插件生命周期正确、新协议接入不修改主体 |
| CAN 原始帧观察 | 虚拟样例源进入正式接收后端，验证帧边界、标准/扩展格式、零长帧、后端提供的远程/错误信息、ID/类型筛选、元数据与字节导出、窗口及会话生命周期；特殊帧可控输入证据单列 |
| UPP/CAN | 相关规范缺口确认后，用有效样例与可控传输验证重组、CRC、字段、交互及原始来源关联；目标硬件互通另做后置验收 |
| TCP | 第三阶段验证拆分/粘连、MBAP、逐连接事务、多 Unit ID、多客户端共享数据与连接隔离 |
| 真实环境 | 独立 Modbus 对端、目标串口及 CAN 适配器的互通/时序验证，与模拟结果分别记录 |

容量、队列、刷新和可持续吞吐验收值由目标环境实测确定并补入对应 issue。模拟测试不代替实际串口时序验证；仅本工具主从互通不能独自证明协议一致性。

## Out of Scope

- 用户协议编辑器、通过 JSON 定义任意协议、同端口多协议同时运行或运行中切换协议。
- 修改既定 UPP、臆造线格式或分片规则、未定义的 UPP 串口/网络承载、任意协议与传输自由组合。
- UDP 产品后端及支持表外的协议/功能码；后续可按明确支持组合扩展。
- 设备写入自动重试、断线后补发未确认写入、复杂自动故障恢复工作流。
- 插件热替换/卸载、任意构建版本之间的二进制兼容、进程隔离插件运行时。
- 首版 QML 绘图、全面切换 Qt Quick、Windows x64 之外的平台交付。
- 首版 Redis 集成、无限记录、任意负载无损记录或未经测量的吞吐保证。
- 工作区内嵌模拟数据作为启动兜底、外部文件热加载、JSON 导入自动合并、以保存文件代替设备写入。
