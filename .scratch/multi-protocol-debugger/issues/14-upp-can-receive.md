## 14A 原始经典 CAN 帧观察

切片状态：`ready-for-agent`（范围已确认；执行仍依赖 UI13 软件收尾）。本项顶部 `needs-info` 表示14B及完整 UPP 目标仍有资料缺口，不阻塞14A。

操作流程：重启加载配套 CAN 传输与帧观察插件 → 新建 CAN 原始帧观察会话 → 配置并显式连接虚拟 CAN 通道 → 单独启动随项目提供的样例源 → 查看帧、筛选和导出 → 停止会话释放端点。

虚拟 CAN 样例源是独立软件测试工具，明确标注测试来源；正式产品接收路径与后续硬件后端共用。首片不新增抓包文件导入、定时回放、UPP 发送按钮或产品通用发帧面板。

### 用户可见行为

- [ ] 沿用已接受的会话浮动/停靠、左侧操作栏、右侧主要数据区和底部通信记录。主表展示每帧时间、方向、CAN ID、标准/扩展格式、帧类型、数据长度及十六进制字节。
- [ ] 明确标为“CAN 原始帧观察”，不冒充已经解析 UPP；CAN ID 仅显示及筛选，不映射设备地址，未知源设备不伪造参数值。
- [ ] 覆盖经典 CAN 标准帧与扩展帧，每帧数据最多8字节；远程帧、错误帧按后端实际提供的信息保留和标识，缺失信息标为不可用。CAN FD 不在首片范围，遇到不支持输入明确提示/记录，不截断后伪装经典帧。
- [ ] 支持 CAN ID、帧格式/类型筛选；筛选只改变显示与所选导出范围，不改变接收和原始记录采集。筛选、导出及来源归属保持同一会话。
- [ ] CSV 概要包含足以区分帧的 ID、格式/类型、长度和原始字节；JSONL保留原始字节、实际元数据及来源。导出范围明确，记录过期或过载缺失沿用现有提示。
- [ ] 提供可重复启动的虚拟 CAN 样例源和操作说明，无硬件时可走完整接收、查看、筛选、导出流程；不自行启动样例流，不把测试数据写成真实设备流量。
- [ ] 停止、关闭、重连及工作区恢复沿用现有会话规则；恢复工作区不自动连接或启动样例源。CAN观察与RTU会话可同时运行且记录隔离。

### 必要接口及记录边界

- CAN 后端通过 Qt SerialBus 接收，每次输入保留一帧边界及实际元数据；不能把 CAN 伪装成 `byte-stream` 来绕过能力判断。
- 主体只做通用的协议/传输能力匹配与帧输入支持，不按 UPP 或 CAN 插件名字增加业务分支。必要接口演进验证现有 RTU 插件兼容与配套构建。
- 保留零字节数据帧以及后端提供的无数据远程/错误帧；数据长度、后端声明长度与可用标志按来源区分，不从 payload 长度编造所有字段。
- 时间区分宿主观测时间与后端提供的时间信息，来源与精度不明时不标为硬件时间。
- 原始帧进入统一记录链；观察插件使用原始记录呈现，不创建虚假的 UPP Message 或成功读取 Operation。CAN专属信息仍在元数据中。
- 首片产品不发送业务报文，不以它为理由提前改造整个发送接口。只观察也不等于承诺硬件电气层的静默/监听模式，具体后端能力另行说明。

### 软件验收

- [ ] 通过既有调试会话公开入口及可控帧输入，验证帧边界、标准/扩展格式、零长度、远程/错误信息、元数据回溯与筛选导出；保持记录容量有界。
- [ ] 在本机实际启动 Qt 虚拟 CAN 样例源及正式 CAN 接收后端，完成真实 Qt 界面操作验收；Qt插件已安装不等于该链路已验证。
- [ ] 虚拟 CAN 后端不能产生的特殊帧以可控输入补测，报告明确区分证据来源，不能伪称虚拟链路已收到该特殊帧。
- [ ] 运行相关 Debug/Release 回归，覆盖 RTU 原行为、多会话隔离、关闭释放、旧回调隔离及插件生命周期；不将软件检查记为物理验收。

## 14B UPP 接收重组与解析

切片状态：`needs-info`。依赖14A完成，并确认 [UPP/CAN 资料](../../../docs/protocols/upp-can-format.md) 中影响本切片的 CAN ID/方向/重组键、CRC参数与有效向量、长度编码、分帧边界/超时、地址/序号及异常格式。

按确认后的规则从实际 CAN 帧重组完整 UPP 报文、校验和解析，建立消息与所有来源帧的关联，按协议插件定义显示字段和失败原因。具体首批功能码及测点映射留待此阶段澄清；不把14A的确认扩大为全部UPP功能授权，也不先假设CRC或分帧策略。

本项交付可验收的完整流程，包含必要界面、数据与协议/传输协作和测试。规格用户故事：7、45、46、53、56、57、62、63、67。

## 验收条件

- [ ] 软件阶段：基于既定规范和样例，以可控 CAN 传输验证接收、解析、错误回溯及插件视图，记录字段预期；完成后可解除15的软件依赖。
- [ ] 后置物理阶段：在目标适配器及驱动上核验真实接收、CAN 元数据与实际时序；未执行前本项不得记为全部完成。

- [ ] 先核对既有 ID、帧、寻址、校验和时序规则及 COMMS 候选适用性，不改协议或编造字段。
- [ ] CAN 经统一通道和记录进入 UPP 插件，专用字段/视图由插件提供，通用 Message 不加入 CAN 专属字段。
- [ ] 验证真实报文与原始来源对应；接入不增加主体按协议名判断，确需 SDK 演进时记录依据。

- [ ] 通过调试会话公开接口验证本项外部行为，附必要界面流程证据；记录实际执行的测试、环境与未覆盖条件。

## 验证方式

以调试会话的启动/停止、操作提交、数据导入/修改及公开查询为主要入口，观察结果、发送数据和回溯证据，底层按需注入可控传输与时钟。仅在契约不能通过该入口验证时补充插件加载或界面边界验证；不测试私有容器和辅助函数调用顺序。真实串口/CAN 与独立对端的证据和模拟测试分开记录。

UPP 资料可以提前整理，但产品实现须遵循 RTU → UPP/CAN → TCP。UPP 不可修改，不预设未提供的 ID、分片、路由或请求/应答规则；资料不足时保持阻塞。
