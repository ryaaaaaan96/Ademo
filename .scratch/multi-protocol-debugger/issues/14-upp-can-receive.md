# 14：通过插件接收并解析真实 UPP/CAN 消息

Status: needs-info
Stage: UPP/CAN
Blocked by: [13 验收 RTU 第一阶段的真实互通与负载](13-rtu-phase-acceptance.md)

## What to build

重启加载 CAN 与 UPP 插件，在界面查看真实消息字段、原始 CAN 元数据和解析失败原因。

本项交付可验收的完整流程，包含必要界面、数据与协议/传输协作和测试。规格用户故事：7、45、46、53、56、57、62、63、67。

## 依据与边界

依据：[正式规格](../spec.md)、[领域术语](../../../GLOSSARY.md)、[架构基线](../architecture.md)、[接口契约](../interface-contracts.md)。当前编号以 [实施索引](../implementation-plan.md) 为准。

- 沿用已验证的 Windows x64、Qt 6.12.0 LLVM-MinGW、Clang 22.1.7、C++17、CMake 3.30.5、Ninja 1.12.1 和 VS Code，见 [环境证据](../toolchain-environment.md)。已有验证不重复列为待办；正式产品与插件仍需本项相关验证。
- 主体管理会话/通道/记录，协议负责协议交互及专用界面；只扩展本流程必要能力。一会话一个端点、一种协议，可有多个设备；设备写入不自动重试。
- UI 采用 Widgets；测试 Adapter 不列为真实支持组合。未进入本项的后续能力保持在对应 ticket，不把本项扩成完整框架。

## 外部条件

UPP 既定规范、真实报文及字段预期、目标 CAN 型号/驱动和可用接收来源。

当前尚未获得足以完成本项验收的资料或环境证据，故标为 needs-info。补齐并记录条件后可转为 ready-for-agent；开始实施仍须满足 Blocked by。不要将模拟结果写成真实硬件或清洁环境验收。

## 验收条件

- [ ] 先核对既有 ID、帧、寻址、校验和时序规则及 COMMS 候选适用性，不改协议或编造字段。
- [ ] CAN 经统一通道和记录进入 UPP 插件，专用字段/视图由插件提供，通用 Message 不加入 CAN 专属字段。
- [ ] 验证真实报文与原始来源对应；接入不增加主体按协议名判断，确需 SDK 演进时记录依据。

- [ ] 通过调试会话公开接口验证本项外部行为，附必要界面流程证据；记录实际执行的测试、环境与未覆盖条件。

## 验证方式

以调试会话的启动/停止、操作提交、数据导入/修改及公开查询为主要入口，观察结果、发送数据和回溯证据，底层按需注入可控传输与时钟。仅在契约不能通过该入口验证时补充插件加载或界面边界验证；不测试私有容器和辅助函数调用顺序。真实串口/CAN 与独立对端的证据和模拟测试分开记录。

UPP 资料可以提前整理，但产品实现须遵循 RTU → UPP/CAN → TCP。UPP 不可修改，不预设未提供的 ID、分片、路由或请求/应答规则；资料不足时保持阻塞。
