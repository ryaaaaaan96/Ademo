# 15：完成真实 UPP/CAN 发送交互并与 RTU 并行

Status: needs-info
Stage: UPP/CAN
Blocked by: [14B UPP 接收重组与解析的软件阶段](14-upp-can-receive.md)；既定发送与交互规则（仅14A原始帧观察完成不足以解除依赖）

## What to build

通过插件操作面板发送一组真实 UPP 消息，按规范显示接收结果或应答，并与 RTU 会话同时运行。

## 与首个 CAN 切片的关系

用户已确认先实施旧14中的14A原始经典 CAN 帧观察，以虚拟 CAN 样例源验收。样例源发帧仅用于测试正式接收链，不代表本项已实现 UPP 发送、设备写入或协议确认。本项保持 `needs-info`；完成14B并确认交互规则后再细化首个发送闭环。

已收到 [UPP报文整理](../../../docs/protocols/upp-can-format.md)，当前缺的是其中列明的协议细节及有效样例，不是等待整份文档。需重点核对发送ID/帧格式、CRC、末帧与长度规则、序号和响应关联；设备写入仍不自动重试。原文只列以太网的功能不得自动纳入CAN范围。

现有发送接口仅传字节，缺少每帧 CAN 元数据。进入本项时应以通用发送契约演进承载必要 ID、格式及标志，并验证 RTU 行为兼容；不得把这些字段私自前缀到 UPP payload 或硬编码在主体。首片观察无需提前为本项实现发送能力。

本项交付可验收的完整流程，包含必要界面、数据与协议/传输协作和测试。规格用户故事：3、18、19、46、47、56、57、62、63、67。

软件阶段需要依据既定协议的发送样例和交互预期，使用可控传输与软件对端验证。真实设备、目标 CAN 适配器和现场交互条件后置，不阻塞软件阶段。

当前尚缺协议交互资料，故保留 needs-info；补齐后仍须满足14的软件依赖。软件验收与后置物理验收分开记录，不将模拟结果写成真实硬件验收。

## 验收条件

- [ ] 发送 ID、字段、必要分片与计时均依据既定规范；不预设协议一定存在请求/应答。
- [ ] 区分发送提交、本地完成与协议确认，未知指令不猜测重试资格，设备写入不自动重试。
- [ ] 软件阶段：依据协议预期，用可控传输与软件对端验证发送、失败回溯、RTU 并行隔离及插件扩展；通过后可进入 TCP 软件阶段。
- [ ] 后置物理阶段：记录目标 CAN 适配器和设备上的真实交互及并行隔离证据；未执行前本项不得记为全部完成。

- [ ] 通过调试会话公开接口验证本项外部行为，附必要界面流程证据；记录实际执行的测试、环境与未覆盖条件。

## 验证方式

以调试会话的启动/停止、操作提交、数据导入/修改及公开查询为主要入口，观察结果、发送数据和回溯证据，底层按需注入可控传输与时钟。仅在契约不能通过该入口验证时补充插件加载或界面边界验证；不测试私有容器和辅助函数调用顺序。真实串口/CAN 与独立对端的证据和模拟测试分开记录。

UPP 资料可以提前整理，但产品实现须遵循 RTU → UPP/CAN → TCP。UPP 不可修改，不预设未提供的 ID、分片、路由或请求/应答规则；资料不足时保持阻塞。
