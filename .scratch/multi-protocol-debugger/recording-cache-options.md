# 回溯缓存与 Redis 评估

Status: needs-triage

2026-10-22 根据 Redis 官方资料核验。Q36 已确认优先保持通信、首版本地有界缓存和后台批量记录，Redis 留作实测后可选后端。本文件不代表已选择、安装或验证 Redis 的实际性能。

## 已确认的首版方案

Redis 保留为后续可选记录后端。首版使用进程内有界缓存、后台批量记录和界面批量刷新，先测清采集、协议处理、记录序列化、磁盘写入和界面刷新各自的耗时。独立记录进程或多个工具共享记录出现实际需求时，再比较 Redis 后端与本地实现。

该建议与 RTU → UPP/CAN → TCP 的阶段顺序配合；第一阶段不要求 Redis 服务。回溯服务内部保留记录写入与存储实现的分离，不额外承诺首版存储插件 SDK。

## 已核验的事实

- Redis 是客户端/服务端系统，即使在本机也有命令往返与 socket 调用。Pipelining 能通过批量命令减少这些成本，批量回复自身也占内存；这不是比进程内缓存更快的证据。[Redis pipelining](https://redis.io/docs/latest/develop/using-commands/pipelining/)
- Redis 可配置 `maxmemory` 及淘汰策略；`noeviction` 达上限后会拒绝新增写入，持久化或复制缓冲还需预留内存。[内存与淘汰](https://redis.io/docs/latest/develop/reference/eviction/)
- Redis 可使用 RDB、AOF 或关闭持久化，恢复范围和写入成本不同。启用 Redis 持久化仍然涉及磁盘写入。[持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)
- 当前官方 Windows 安装页提供 Docker 路径，并列出合作产品 Memurai 的 Windows 路径。因此本工具若依赖 Redis，还要选择并交付相应服务环境；不能将其当作一个直接嵌入 Qt 应用的普通内存容器。[Windows 安装](https://redis.io/docs/latest/operate/oss_and_stack/install/install-stack/windows/)
- Redis Streams 支持追加、裁剪和消费者组读取，可用于跨进程记录流；记录的关联、过期与丢失提示仍由本工具定义。[XADD](https://redis.io/docs/latest/commands/xadd/)、[XREADGROUP](https://redis.io/docs/latest/commands/xreadgroup/)

## 对本工具的工程判断

以下是基于上述机制的推论，尚未做性能实测。

| 实测瓶颈或需求 | 优先处理方向 | Redis 的可能作用 |
| --- | --- | --- |
| 界面逐条插入导致卡顿 | 合并刷新、限制可见数据量、减少模型通知 | 不直接解决 GUI 渲染成本 |
| 通信线程被解析、记录或同步等待占用 | 分离耗时工作，限制每轮处理量和队列增长 | 同步等待 Redis 反而可能新增阻塞 |
| 短时记录突发 | 本地有界缓存、批量写入，测量队列峰值 | 独立进程缓冲可作为对照方案 |
| 持续输入速度高于落盘速度 | 降低记录开销、改善存储吞吐，明确溢出处理 | 同机增加缓存通常只能延后积压，不能无限吸收 |
| 多进程或多个工具共享记录 | 明确跨进程传输和消费边界 | Streams 等机制有明确的评估价值 |

任何方案都不能恢复采集前已经丢失的字节。必须区分硬件/后端报告的接收丢失、工具内记录队列溢出和历史容量轮换，不能用一个“缓存正常”指标掩盖全部情况。

## 接入约定（Q36 已确认）

通信处理向回溯服务提交带身份和时间的记录，写入后端在后台消费有界队列，界面按批次更新展示模型。首版由本地缓存与文件记录实现；以后若采用 Redis，由该后台写入边界接入，协议插件和传输插件不直接依赖 Redis 客户端。

队列满、后端不可用或持续落后时，通信路径不等待存储恢复。按所选记录策略保留可用记录，并明确提示未记录数量、范围及不可回溯关联；缓存历史正常过期另行标识。不能承诺后端故障或过载期间无损，也不能使用无限队列。

先测队列长度/峰值、协议处理耗时、界面刷新耗时、序列化与落盘吞吐、记录丢失计数。只有确认 Redis 对实际瓶颈有收益，且额外部署成本可接受时，再决定具体客户端、批量大小、持久化和容量策略。
