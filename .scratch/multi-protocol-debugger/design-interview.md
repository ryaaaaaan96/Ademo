## 已明确的目标与项目约定

- 构建类似 Modbus Poll / Slave 的 Qt 桌面调试工具，支持 Modbus 和自定义协议 UPP。
- UPP 当前运行在 CAN 上；未来希望增加串口、以太网和新协议时，无须修改已有代码，或仅需简单扩展。
- 中文交流与文档；issue 使用本地 Markdown，保留默认分诊标签。
- 保留 single-context 文档布局：根目录 `GLOSSARY.md` 与 `docs/adr/`。

## 当前已确认结论（Q36 已收束通用架构）

本节为当前基线，优先于后文保留的历史提问和初始接口。

- **Q6：通过加载协议插件兼容新协议，不修改主体。** 暂不提供用户自定义协议编辑器。
- **Q7：采用路线 A，统一传输与记录。** Modbus 与 UPP 各自组包和管理协议交互；组件选型及具体接口继续细化。参见 [ADR 0002](../../docs/adr/0002-shared-transport-and-recording.md)。
- **Q8：插件在重启后加载。** 协议和传输都有插件接入点，插件按配套版本交付。参见 [ADR 0003](../../docs/adr/0003-restart-loaded-extension-plugins.md)。
- **Q9：按第二轮支持表验收。** Modbus TCP 与 RTU 均包含主站读写/轮询和从站寄存器模拟/应答；UPP/CAN 实现一组真实消息的发送、接收与解析。
- **Q10：支持多个调试会话同时运行，包括同时运行 Modbus 主站和从站。** 会话分别维护连接和状态；端点占用按 Q13/Q18/Q19 约定处理。
- **Q11/Q26：近期记录有容量上限，支持手动导出；用户可主动开启磁盘记录用于长期或跨重启回溯。** 缓存与磁盘容量可配置，达到容量后淘汰最旧记录并提示；支持 CSV 概要和 JSONL 完整记录导出。容量初始值与性能预算留待验证。
- **Q12：采用插件提供协议交互、配置/操作声明与可选专用视图的边界。** 主体管理会话生命周期、通道、记录和通用界面。见 [ADR 0004](../../docs/adr/0004-protocol-owned-interaction-and-views.md)。
- **Q13/Q18：一个会话管理一个端口/配置端点，使用一种协议，支持该协议下的多个设备。** 首版不实现同端口多协议，设备与端点的具体映射已在 Q19 确认。
- **Q14：采用 TraceRecord、Message、Operation 分别建模并关联。** 见 [ADR 0005](../../docs/adr/0005-separate-traces-messages-and-operations.md)。
- **Q15/Q20：仅读取可自动重试，设备写入和参数设置不自动重试。** 重试次数与时间统一在会话级配置，不提供设备级覆盖。此结论由用户澄清，替代此前“读写都可重试”的选择。见 [ADR 0007](../../docs/adr/0007-session-read-retries-and-operator-recovery.md)。
- **Q16：采用主站观测值与从站模拟数据分离、按 Unit ID 维护四类数据区的模型。** 同一从站实例对多个 TCP 客户端共享模拟数据，首版功能码为十六进制 01/02/03/04/05/06/0F/10 及对应异常响应。
- **Q17/Q23：首版采用 Windows x64、Qt 6、CMake 和 Qt Widgets。** 后续绘图面板可用 QQuickWidget 嵌入 QML；视图对宿主提供 QWidget 容器，协议核心继续采用 C++。见 [ADR 0006](../../docs/adr/0006-widgets-shell-with-optional-qml-panels.md) 与 [界面工具包对比](ui-toolkit-comparison.md)。
- **Q19：采用一端点一会话的多设备映射。** RTU 一个串口管理多个从站地址；TCP 主站一个远端 IP:port 一个会话，其下可以有多个 Unit ID，不同远端分别开会话；TCP 从站一个监听端点向多个客户端提供多个模拟 Unit ID。
- **Q21：断线结束当前未完成操作，允许配置自动重连，重连后恢复轮询。** 已提交但未确认的写操作不自动补发。界面状态保持简单，主要恢复操作交给操作人员，底层细节保留在日志中。
- **Q22/Q30：工作区保存会话、设备、轮询、会话通信/重试配置、布局及外部从站数据文件的引用。** 打开工作区先恢复配置，由操作人员启动通信；从站启动时加载外部 JSON，缺失时不启动。此结论替代此前可选内嵌从站快照的安排，不以工作区副本或零值替代缺失文件。见 [ADR 0008](../../docs/adr/0008-external-slave-data-files.md)。
- **Q24：会话默认额外读取重试 2 次、单次应答超时 1000 ms、重试间隔 100 ms，均可修改。** 次数不包含首次发送，配置 2 次即最多尝试 3 次，0 次表示不自动重试；轮询周期独立配置。设备写入/参数设置仍不自动重试。
- **Q25/Q27：Modbus 数据支持手动编辑、JSON 导入，导入后可以继续修改，并提供保存按钮。** 首版一个从站数据文件对应一个 Modbus 从站设备，包含四类数据区、地址范围和数值；多设备与连接配置继续由工作区保存。用户明确允许在设计过程中按需扩展 JSON 字段，当前不冻结字段清单；该需求属于已有协议的数据配置，不增加协议编辑器。
- **Q28：导入先校验，通过后整体替换目标数据，有未保存修改先提示，失败保留原数据。** 保存写回当前 JSON，新建数据首次保存选择路径，并提供另存为；首版不做自动合并。文件保存与向真实设备写入分别操作。
- **Q29/Q31：运行中的从站数据编辑、整份 JSON 导入和地址范围调整，校验成功后立即用于后续请求，无须停止会话或先保存文件。** 替换只作用于目标设备，一条请求使用一致的数据视图；校验失败保留原数据。
- **Q32：仅在启动会话或主动导入时读取外部 JSON；运行中外部修改或删除文件不自动影响已加载数据。** 下一次启动重新加载和校验，该会话所需文件全部有效才启动；缺失、无法读取或格式错误只阻止对应会话，软件界面及其他会话仍可使用。错误提示设备、路径和原因，重新加载前有未保存修改时提示保存、放弃或取消。
- **Q33：插件缺失、不兼容或加载失败时，仅禁用依赖该插件的功能和会话，其他功能继续使用。** 提示失败原因并保留工作区配置；修复插件、重启应用后恢复使用，保存工作区不能丢弃暂时无法解释的插件配置。
- **Q35：实施顺序改为 Modbus RTU → UPP/CAN → Modbus TCP。** 第一阶段随 RTU 主从闭环建设公共宿主、传输与记录；第二阶段依真实 UPP 规范接入 CAN；TCP 保留到最后阶段，不作为 RTU 的前置工作。
- **Q34/Q36：优先保持通信，首版采用进程内有界缓存、后台批量记录和界面批量刷新。** 队列溢出时明确提示记录丢失，正常历史过期另行标识；Redis 仅作为实测后可选的异步记录后端，不作为首版依赖。用户确认以此及既定阶段顺序作为通用架构基线。见 [ADR 0009](../../docs/adr/0009-communication-first-bounded-recording.md)。
- **UPP 规范稍后提供。** 继续推进独立于 UPP 线格式的架构设计；CAN ID、分片、路由与应答规则留待规范核验。

| 协议与传输 | 首版能力 |
| --- | --- |
| Modbus TCP | 主站读写、轮询；从站寄存器模拟与应答 |
| Modbus RTU / 串口 | 主站读写、轮询；从站寄存器模拟与应答 |
| UPP / CAN | 按真实协议完成一组消息的发送、接收和解析 |

## 用户初始方案（待验证）

### 三层边界

```text
UI：报文列表 / 发送面板 / 寄存器视图
  ↕ 统一 Message
协议：Modbus Codec / UPP Codec / 后续协议
  ↕ 原始字节 + TransportMeta
传输：CAN / 串口 / TCP / UDP
```

传输层仅收发字节；协议层仅编解码；UI 仅消费 Message，不直接访问传输。

### 候选选型

| 用途 | 候选 | 初始理由 |
| --- | --- | --- |
| CAN | Qt Serial Bus / QCanBus | 插件式硬件适配 |
| 串口 | Qt Serial Port | 异步串口 |
| TCP / UDP | Qt Network / QTcpSocket / QUdpSocket | 与事件循环集成 |
| Modbus | QModbusClient / QModbusServer，备选 ModbusLib | 希望可以更换实现而保持接口 |
| UPP | CommsChampion COMMS Library | 声明式报文定义与序列化 |
| UI 参考 | xTools | 借鉴交互与布局 |

### 候选接口

```cpp
class TransportBackend : public QObject {
    virtual bool send(const QByteArray &data, const TransportMeta &meta) = 0;
signals:
    void received(const QByteArray &data, const TransportMeta &meta);
};

class ProtocolCodec : public QObject {
    virtual QList<Message> feed(const QByteArray &data, const TransportMeta &meta) = 0;
    virtual QByteArray encode(const Message &msg, TransportMeta *outMeta) = 0;
};
```

- TransportMeta：时间戳、通道、CAN ID、DLC 等可选信息。
- Message：方向、时间戳、原始字节、解析字段树。
- CAN 专用信息留在 TransportMeta，不进入 Message 定义。
- 接收时，CAN 后端填充元数据，UPP Codec 按需读取。
- 发送时，UPP Codec 给出 CAN ID，CAN 后端据此组帧；草案提出串口和网络后端忽略该字段。
- 若 UPP 的路由依赖 CAN ID，需要定义其他传输上的等价字段。

### 候选扩展方式

- 新传输：实现 TransportBackend 子类并注册。
- 新协议：实现 ProtocolCodec 子类并注册。
- Modbus 新功能码：在协议模块内扩展。
- UPP 新消息：新增 COMMS 定义，期望 Codec 自动支持。

### 候选实施顺序

1. CAN 后端与最小 UPP Codec，控制台验证收发解析。
2. Modbus Codec 与 TCP 后端，验证接口复用。
3. 报文列表、发送面板、寄存器视图，验证切换协议和传输时 UI 核心稳定。
4. 串口、UDP、多传输并存及 CAN 语义处理。

## 第一轮问题与建议（历史，已回答）

1. Q1：首版先完成 UPP over CAN 的收发解析，以及 Modbus TCP 主站的读写/轮询；从站模拟后续补齐，是否接受？建议接受，以两条实际链路验证复用。
2. Q2：扩展承诺定义为允许重新编译、新增适配器/描述文件/注册项，而已有传输、协议和 UI 核心逻辑不必修改，是否接受？建议接受；动态加载另行决定。
3. Q3：报文列表和导出需要保留 CAN ID、帧标志等传输信息，并保留无法解析或解析失败的数据，是否接受？建议接受，以便定位协议和总线问题。
4. Q4：按明确的协议×传输支持列表开放组合；缺少映射时拒绝组合，是否接受？建议接受；UPP 迁移通道前需要定义对应线格式与路由。
5. Q5：按兼容现有设备的既定 UPP 协议进行设计，不为统一接口改变设备侧 CAN ID 或报文布局，是否符合实际？建议已有设备时采用此约束；如果 UPP 尚可修改，应明确说明。

## 第二轮问题与建议（历史，已回答）

6. Q6：将“通用/非通用协议”明确为“标准协议（Modbus）/自定义协议（UPP）”，两者按同一扩展契约接入，是否符合意图？建议采用此命名；用户配置即可定义任意协议的组包器属于另一项产品能力，需单独决定。
7. Q7：是否优先统一传输与原始记录，让 Modbus、UPP 各自负责组包和协议交互？建议采用此路线以保证调试证据完整；代价是需要自行实现或引入可使用外部 I/O 的 Modbus 编解码/交互组件，并做协议一致性验证。备选是适配现成 QModbus 完整协议栈，以会话接口统一并解决观测需求。两种路线都需要明确轮询、超时和应答管理，纯 Codec 接口不足。
8. Q8：插件是否先采用“放入编译好的插件文件，重启后发现并加载；插件与指定应用/Qt 构建版本配套”的契约？建议如此，同时让协议和传输都拥有插件接入点；运行中安装卸载和跨版本二进制兼容另行评估。
9. Q9：首版是否以 Modbus TCP 与 RTU 均支持主站/从站，加 UPP over CAN 的一组真实消息收发解析作为验收范围？建议此范围；UPP 示例需要真实协议闭环，仅预留空接口不足以验证扩展能力。若 RTU 希望后置，或 UPP 需要完整设备模拟，应明确调整。
10. Q10：是否支持同一应用内同时运行多个独立调试会话，包括同时运行 Modbus 主站和从站？建议支持，各自的连接与调试状态保持隔离。
11. Q11：回溯是否默认保留有容量上限的近期原始记录，支持手动导出；长时间或跨重启回溯由用户主动开启磁盘记录？建议如此，并提示记录保留范围、过期或丢失情况，避免让用户误以为历史永久存在。

## 第三轮问题与建议（历史，已回答）

12. Q12：协议插件是否同时负责协议会话、编解码、配置/操作声明和可选专用视图，而主体负责会话生命周期、通道、记录和通用界面？建议如此，Modbus 寄存器视图归协议插件，主体按能力挂载新协议功能。
13. Q13：首版是否由一个会话拥有一个配置端点，端点内可以有多个设备地址或 TCP 客户端连接，同一物理串口/CAN 通道不隐式分给多个会话？建议先明确独占；TCP 服务端按连接隔离解码状态，RTU 会话按总线统一调度。若首版需要 CAN 多会话共享，应在此明确。

## 技术事实与待定影响

以下为官方文档与源码核验结果；设计推论尚待访谈确认。

1. **QModbus 并非纯编解码器。** QModbusClient 提供异步请求、回复、超时与重试；QModbusServer 维护寄存器映射并处理请求。官方 TCP/RTU 实现自行持有 socket/串口。推论：若优先复用这些实现，可在会话或协议服务层统一；若坚持共享自建 TransportBackend，需要选择支持注入 I/O 的实现或自行实现更多 Modbus 逻辑。Qt 已有 sendRawRequest 等扩展入口，增加功能码并不必然需要换库。
   - [QModbusClient](https://doc.qt.io/qt-6/qmodbusclient.html)
   - [QModbusServer](https://doc.qt.io/qt-6/qmodbusserver.html)
   - [Qt TCP 实现](https://github.com/qt/qtserialbus/blob/dev/src/serialbus/qmodbustcpclient_p.h)
   - [Qt RTU 实现](https://github.com/qt/qtserialbus/blob/dev/src/serialbus/qmodbusrtuserialclient_p.h)
2. **传输边界不同。** CAN 交付帧，TCP/串口提供字节流，UDP 保留数据报边界与对端信息。CAN 还有标准/扩展格式、FD、BRS、错误帧、RTR、本地回显等属性。推论：统一的数据接口需要保留这些语义；只有在协议承载映射明确时才能选择对应传输，不能靠忽略字段保证互通。
   - [QCanBusFrame](https://doc.qt.io/qt-6/qcanbusframe.html)
   - [QTcpSocket](https://doc.qt.io/qt-6/qtcpsocket.html)
   - [QSerialPort](https://doc.qt.io/qt-6/qserialport.html)
   - [QUdpSocket](https://doc.qt.io/qt-6/qudpsocket.html)
3. **发送成功有多个层次。** writeFrame 在部分平台返回成功只代表已入队，framesWritten 也不代表对端业务处理成功。推论：需要后续确定发送请求、传输完成与协议应答的独立状态；UPP 若存在分片，当前单次 encode 的返回形状也需要复核。
   - [QCanBusDevice::writeFrame](https://doc.qt.io/qt-6/qcanbusdevice.html#writeFrame)
4. **COMMS 的自动支持有范围。** 消息必须纳入解析器的消息类型集合，应用需要提供处理函数；声明式定义和分派不等于自动完成轮询、重试、路由或 UI 适配。推论：需要明确新增消息的登记/生成步骤，以及通用字段展示与专用交互的边界。
   - [COMMS 文档](https://commschamp.github.io/comms_doc/)
   - [协议使用教程](https://commschamp.github.io/comms_doc/page_use_prot.html)
5. **QModbus 的底层访问不等于完整捕获契约。** QModbusDevice::device() 可返回底层 QIODevice，TCP Server 也有连接观察器；不能笼统地认为无法访问底层。QModbusReply::rawResult() 返回响应 PDU，intermediateErrors() 反映部分错误，未统一提供每个收发数据块及其通道、原始字节和关联信息。Qt 的 qt.modbus.lowlevel 日志包含报文诊断信息，但没有承诺产品级捕获所需的稳定结构与实例关联。推论：整体复用 QModbus 时，完整原始回溯是需要单独解决的集成问题，不能直接将日志或额外 readyRead 监听当作已满足需求。
   - [QModbusDevice::device](https://doc.qt.io/qt-6/qmodbusdevice.html#device)
   - [TCP 连接观察器](https://doc.qt.io/qt-6/qmodbustcpconnectionobserver.html)
   - [QModbusReply](https://doc.qt.io/qt-6/qmodbusreply.html)
   - [官方日志类别](https://doc.qt.io/qt-6/qtserialbus-index.html#logging-categories)
6. **Qt 支持应用扩展插件，但存在构建兼容约束。** QPluginLoader 支持动态共享库加载及加载前读取元数据；应用需实现自己的发现和筛选。Qt 版本、Windows debug/release 等构建配置影响兼容，静态链接 Qt 的应用不能通过 QPluginLoader 加载动态 Qt 插件。推论：启动扫描、配套 SDK 构建、重启更新是可行的候选交付契约；这仍需用户决定，不能自动推定热插拔或跨版本兼容。
   - [QPluginLoader](https://doc.qt.io/qt-6/qpluginloader.html)
   - [应用插件指南](https://doc.qt.io/qt-6/plugins-howto.html#the-low-level-api-extending-qt-applications)
   - [部署兼容规则](https://doc.qt.io/qt-6/deployment-plugins.html#loading-and-verifying-plugins-dynamically)
