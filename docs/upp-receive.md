# UPP CAN 接收解析（14B暂定软件版）

本页说明用户授权先实施、后续修订的接收观察功能。原始依据见[UPP资料](protocols/upp-can-format.md)，暂定选择见[14B规则](../.scratch/multi-protocol-debugger/14b-provisional-profile.md)。不是已经验证目标设备的正式线格式；observer保留本页接收观察；15新增master发送交互，见[发送说明](upp-exchange.md)。TCP未启动。

## 使用

启动本机Release程序，新建会话并选择“UPP CAN 交互（暂定规则）”、CAN传输和observer。虚拟软件测试使用virtualcan/can0，显式启动会话后由用户另行运行 `run-upp-sample.cmd`。工具不自动生成流量；本轮代理验收只用Qt offscreen，不打开或操纵桌面。

独立样例源通过正式Qt CAN后端发送重复的握手请求与两片握手回复；默认CAN ID为5，命令行可用 `--can-id 321` 改为十六进制321，`--extended`选择扩展帧。报文设备地址仍为5，因此界面设备归属不由CAN ID替代。直接工具参数为 `can_sample_source --profile upp --interface can0 --count 60 --interval 20`；每3帧构成一组完整握手样例。样例只用于软件测试，CRC由独立脚本计算，未冒充设备抓包。

## 配置和方向

- `direction`：auto/request/response。rx只表示工具收到了CAN帧，不表示协议响应。自动模式仅在结构唯一时分类；例如0x21六字节PDU既可能是请求也可能是响应，显示ambiguous-direction并保留证据。
- `requestCanIds` / `responseCanIds`：可选十六进制逗号列表，为对应CAN ID明确方向，优先于direction；重叠列表拒绝启动，设备身份仍取报文。标准/扩展帧均适用该ID配置，分片格式必须一致。
- `fragmentTimeoutMs` / `packetTimeoutMs`：默认100/1000，合法1..60000毫秒，停止、断线、重连清除未完整报文和请求上下文。
- `soeModels`：明确为SOE的模型号，十进制逗号列表。仅0x23响应时标类型A1且模型在该列表中，才按bit0→bit7解出CP56Time2a字段；否则保留数据字节，不猜测测点类型。时区未规定，不生成虚假UTC时间。

暂定长度0表示256，异常码2字节大端，多字节模型/偏移/长度/子序号大端；CRC-16/MODBUS低字节先传。全部CAN功能20/21/22/23/26/27/28及对应异常均支持结构解析；未知型号、单位、比例、有符号性不生成工程值。0x27/0x28以字段表和实际长度为准，不裁定设备读写执行顺序。以太网专用功能不扩入CAN。

## 消息与回溯

主表显示设备地址、序号、功能、方向和状态；选中一条消息可查看字段和该ADU的全部原始分片、CAN元数据。原始记录过期显示不可用，不伪造字节。底部既有通信记录支持完整JSONL/CSV导出，JSONL包含消息、原始帧和sourceRanges。设备筛选仅影响插件表。

一个会话仅重组一个不交错报文；每片同ID/格式、非末片8字节、末片实际剩余长度、无填充，CRC可跨片。续片中0x50不会被猜作新头。缺片/重片可能表现为长度、CRC或超时错误；协议无分片序号，不能承诺检测所有恰好形成合法报文的损坏。

异常/不支持输入保留原始证据与失败原因。远程/错误/FD帧不作为UPP字节。未观察请求的0x21响应保留原始数据且地址上下文标不可用；只有设备/序号/功能匹配、唯一且未过期的上下文才用于关联，重复请求标歧义，响应消费上下文。观察写请求不会执行写入或产生虚假成功Operation。

物理设备互通、CAN驱动与时序留待后续；当前软件通过不代表这些验证完成。
